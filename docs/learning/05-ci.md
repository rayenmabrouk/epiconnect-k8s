# Milestone 6: Continuous integration

What was built: one GitHub Actions workflow, `.github/workflows/ci.yml`, that checks
everything in this repository on every push and pull request, and publishes the
application image only after it has been scanned and seen working with the chart.

```
 lint ─────────────────────────────────────────────┐
 manifests (helm lint, kubeconform) ──┐            ├─> publish to GHCR (main only)
 image (build, Trivy gate) ───────────┴─> smoke ───┘
                                          (k3d)
```

| Job | Runs | Fails when |
|---|---|---|
| lint | `make lint` (yamllint, ansible-lint, shellcheck, zizmor), PSScriptAnalyzer, gitleaks | style/logic errors, unsafe workflow patterns, a secret in the git history |
| manifests | `scripts/validate-manifests.sh` | a manifest or rendered template is not valid Kubernetes 1.36 |
| image | build from `app/`, Trivy | a HIGH/CRITICAL vulnerability with a fix available |
| smoke | `scripts/smoke-test.sh` on k3d | the chart + this image do not install, serve, isolate the DB, upgrade or roll back |
| publish | `docker push` of the tested image | registry permissions (skipped if the tag exists) |

The scripts are the same ones used locally (`make lint`, `make validate`, `make smoke`):
CI adds no logic that cannot be run and debugged on the control machine.

---

## 1. Pipeline order: test, then publish

1. **What:** jobs form a graph (`needs:`): lint, manifests and image run in parallel; smoke needs manifests + image; publish needs lint + smoke.
2. **Why:** the registry is where "released" starts. Anything pushed there can be deployed.
3. **Problem solved:** a broken or vulnerable image being published (and then pulled by the lab) before anyone knows.
4. **How it works:** the image job builds with `load: true` (into the runner's Docker, not a registry), saves it with `docker save`, and uploads it as a workflow artifact. The smoke job loads that file and imports it into k3d; the publish job loads the **same file** and pushes it. The bytes that were tested are the bytes that ship. Publishing runs only for `main` (`if:`), never for pull requests.
5. **Commands:** GitHub → Actions → CI → a run (graph + job summaries) · locally: `make lint && make validate && make smoke`
6. **What can go wrong:** rebuilding in the publish job instead of reusing the artifact (a different image than the tested one: base image or dependency could have changed in between).
7. **Troubleshoot:** open the failed job; every job writes a summary; the smoke test prints diagnostics on failure.
8. **Interview:** "Walk me through your pipeline."
9. **Answer:** "Lint and manifest validation run in parallel with the image build. The image is scanned with Trivy, then installed with the Helm chart on a throwaway k3d cluster and tested end to end. Only if all of that passes, and only on main, is that exact image pushed to GHCR, tagged with the application commit. CI never deploys: the cluster is on a private network, deployment is a local command."

## 2. Lint layer

1. **What:** yamllint (YAML syntax/style), ansible-lint *production* profile (Ansible best practices + `--syntax-check` of every playbook), shellcheck (shell bugs), PSScriptAnalyzer (PowerShell), zizmor (GitHub Actions security), gitleaks (secrets in any commit).
2. **Why:** cheap, fast, and they catch whole classes of bugs before anything runs.
3. **Problem solved:** unquoted variables, typos in YAML, non-idempotent Ansible patterns, template injection in workflows, committed credentials.
4. **How it works:** CI has **no vault password** (by design: GitHub never holds it). The encrypted `vault.yml` is replaced by `vault.yml.example` and a dummy password file, so playbooks can still be syntax-checked. zizmor gets the workflow token so it can run its online audits (e.g. "impostor commit": is each pinned SHA really a commit of that action's repository, not of a fork?). gitleaks needs the full history (`fetch-depth: 0`).
5. **Commands:** `make lint` · `zizmor .github/workflows` · `shellcheck -x scripts/*.sh`
6. **What can go wrong:** ansible-lint failing with `internal-error` when it cannot decrypt the vault; zizmor findings after editing the workflow (e.g. `${{ }}` used inside `run:`).
7. **Troubleshoot:** run the same command locally; for zizmor, the finding names the audit and links its documentation.
8. **Interview:** "How do you lint Ansible code that uses Vault in CI without giving CI the password?"
9. **Answer:** "I keep a documented example of the vault with placeholder values. In CI the encrypted file is swapped for the example and a dummy password is configured, so syntax checks and lint run on the real playbooks while the real secrets never leave my machine."

## 3. Manifest and chart validation

1. **What:** kubeconform validates every raw manifest and the chart rendered with two sets of values (lab, CI) against the JSON schemas of Kubernetes **1.36.4** in *strict* mode; `helm lint --strict` checks the chart.
2. **Why:** a typo in a field name is otherwise silently ignored by some tools or only discovered at deploy time.
3. **Problem solved:** `replica: 3` instead of `replicas: 3` (would deploy 1 replica), fields at the wrong indentation, API versions that no longer exist.
4. **How it works:** kubeconform downloads the OpenAPI-derived schema for each kind/apiVersion and validates offline; `-strict` rejects unknown fields (`additionalProperties: false`). It needs no cluster. It does **not** run admission (Pod Security, webhooks): `make helm-check` (server-side dry run against the lab) and the smoke test do.
5. **Commands:** `make validate` · `helm template epiconnect helm/epiconnect -n epiconnect | kubeconform -strict -summary -kubernetes-version 1.36.4 -`
6. **What can go wrong:** schema version newer/older than the cluster (false passes/fails); CRDs have no built-in schema (not used here).
7. **Troubleshoot:** the error names the object and the JSON path of the bad field.
8. **Interview:** "How do you validate Kubernetes manifests in CI without a cluster?"
9. **Answer:** "Schema validation with kubeconform, strict mode, pinned to the cluster's version, on both the raw YAML and the rendered Helm chart. For admission-level checks I also do a server-side dry run against the real cluster when I have access, and a full install on an ephemeral cluster in CI."

## 4. Image vulnerability gate (Trivy)

1. **What:** Trivy scans the built image (OS packages + Python libraries + embedded secrets). The build fails on any HIGH or CRITICAL vulnerability **that has a fixed version available**.
2. **Why:** fixable vulnerabilities are the ones attackers use first, and the ones we can act on.
3. **Problem solved:** shipping an image with a known, patched vulnerability.
4. **How it works:** Trivy compares package versions in the image with its vulnerability database. `ignore-unfixed` drops findings with no patch (nothing to do yet); accepted risks go in `app/.trivyignore`, owned by the EPIConnect repository, which applies the same gate: one policy for both repositories. The EPIConnect Dockerfile already runs `apt-get upgrade` and removes pip for this reason.
5. **Commands:** `trivy image --severity HIGH,CRITICAL --ignore-unfixed ghcr.io/rayenmabrouk/epiconnect:<tag>`
6. **What can go wrong:** a new CVE published overnight fails a build that passed yesterday (that is the point); the vulnerability database download is rate-limited.
7. **Troubleshoot:** read the table in the job log: package, installed version, fixed version. Update the base image or dependency in EPIConnect.
8. **Interview:** "A scan fails on a CVE in a library you don't even call. What do you do?"
9. **Answer:** "First check whether a fixed version exists and just upgrade. If the risk really doesn't apply, I add it to the ignore file with the reason and a review date, in a reviewed commit, so the exception is visible and expires; I don't lower the gate."

## 5. Smoke test on an ephemeral k3d cluster

1. **What:** k3d runs k3s nodes as Docker containers. CI creates a 1-server + 1-agent cluster with the lab's k3s version, labels the nodes like the lab (`pool=data`, `pool=app`), installs the chart with the image just built, and checks: install with migrations, scheduling, HTTPS through Traefik, NetworkPolicy isolation, upgrade (config change rolls the pods, new migration Job), rollback.
2. **Why:** schema validation cannot tell whether the app actually starts under Pod Security *restricted*, whether probes pass, or whether the NetworkPolicies let the app reach its database.
3. **Problem solved:** "valid YAML, broken system": discovered in CI instead of on the lab.
4. **How it works:** the only chart difference is storage for uploads: no NFS server exists, so `ci/smoke-values.yaml` sets `media.nfs.server: ""` and the chart creates a ReadWriteOnce claim instead (valid because all web pods run on the one agent). The script writes its **own kubeconfig** in a temp directory, so it can never touch the lab cluster, whatever `KUBECONFIG` says.
5. **Commands:** `make smoke` · `KEEP_CLUSTER=1 make smoke` then `k3d cluster list`, `k3d cluster delete epiconnect-smoke`
6. **What can go wrong:** Docker Hub rate limits (k3s, postgres, busybox images); timeouts on a slow runner; NetworkPolicy enforcement lag (the probe retries).
7. **Troubleshoot:** the diagnostics block (pods, events, logs, helm history); reproduce locally with `KEEP_CLUSTER=1`.
8. **Interview:** "What does your smoke test prove, and what doesn't it?"
9. **Answer:** "It proves the chart and the image work together on the same Kubernetes distribution and version as my lab, with the same security policies: install, HTTPS, database isolation, upgrade and rollback. It doesn't prove anything about multi-node behaviour, shared NFS storage or node failures: that's what the lab demos are for."

## 6. Supply chain: what CI runs is pinned

1. **What:** actions pinned to full commit SHAs; downloaded tools pinned to a version **and** a SHA-256 written in `scripts/install-tools.sh`; Python tools pinned in `requirements-tools.txt`.
2. **Why:** a tag (`@v3`, or a release asset) can be moved or replaced by whoever controls the upstream repository, legitimately or not.
3. **Problem solved:** in March 2026, attackers force-pushed most tags of `aquasecurity/trivy-action` and published a malicious Trivy binary ([GHSA-69fq-xp46-6x23](https://github.com/advisories/GHSA-69fq-xp46-6x23)); workflows referencing those tags ran credential-stealing code. A commit SHA cannot be re-pointed, and a checksum stored in *this* repository cannot be changed without a commit here.
4. **How it works:** `sha256sum --check` against the committed value before anything is executed. (A checksum file downloaded from the same release only proves the download is intact, not that the release is genuine.) kubectl is checked against the checksum published by the Kubernetes release infrastructure on `dl.k8s.io`. Trivy runs through `trivy-action` pinned to the same post-incident commit as the EPIConnect repository.
5. **Commands:** `scripts/install-tools.sh ~/.local/bin kubeconform` · `git log -p scripts/install-tools.sh` (every version bump is reviewable)
6. **What can go wrong:** pinned versions go stale (no automatic updates here).
7. **Troubleshoot:** a checksum mismatch is a stop signal, not something to "fix" by pasting the new hash.
8. **Interview:** "How do you protect a pipeline against a compromised third-party action?"
9. **Answer:** "Pin actions to commit SHAs, give each job the least permissions it needs (only the publish job can write packages), pin downloaded tools to checksums stored in the repo, and scan the workflow itself with zizmor. The Trivy incident this year is exactly the case: tag-pinned workflows were compromised, SHA-pinned ones were not."

## 7. Publishing: immutable tags, least-privilege token

1. **What:** the publish job logs in to GHCR with the workflow's own `GITHUB_TOKEN`, checks whether `epiconnect:<EPIConnect commit>` already exists, and pushes only if it does not.
2. **Why:** a tag names one application commit; it may already be running in the lab. Changing what it points to would make rollbacks and "what is running?" unreliable.
3. **Problem solved:** silently different images behind the same tag (non-reproducible builds produce a new digest every time).
4. **How it works:** workflow-level permission is `contents: read`; only the publish job adds `packages: write`, and it runs only on `main`. No long-lived registry password exists.
5. **Commands:** `docker manifest inspect ghcr.io/rayenmabrouk/epiconnect:0b3cd06` · Actions → workflow dispatch with `app_ref` to build another EPIConnect version
6. **What can go wrong:** re-running on the same app commit reports "already published": expected.
7. **Troubleshoot:** a new image needs a new app commit (submodule bump or `app_ref`).
8. **Interview:** "Why not just push `latest` on every build?"
9. **Answer:** "Because then the tag tells you nothing and changes under you. My tags are the application commit and are never overwritten, so any running pod maps to exactly one source commit, and a Helm rollback really returns to the previous image."

## 8. Why CI does not deploy

See [D23](../DECISIONS.md) and section 11 of [03-kubernetes-manifests.md](03-kubernetes-manifests.md). Short version: the cluster is private, inbound access for GitHub would be the wrong trade-off; production would use a pull-based GitOps agent or a runner inside the network.
